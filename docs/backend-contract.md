# Бо Хам — что нужно от бэкенда (контракт с iOS-клиентом)

Состояние клиента — ветка `claude/eloquent-bell-acbxkp`. Всё ниже клиент **уже умеет**. Новые поля он читает как необязательные: пока сервер их не присылает, функция просто скрыта и ничего не ломается. Поэтому раздел можно делать по частям, в любом порядке.

Общие правила, на которые опирается клиент:

- Ошибки: `{ "message": string | string[], "code"?: string }`. Если в `code` пришёл `videoTooLong` или `fileTooLarge`, клиент показывает свой текст на языке интерфейса. В остальных случаях он показывает `message` от сервера.
- Любое новое поле в ответе — опциональное. Незнакомые значения enum-подобных строк клиент игнорирует. Исключение — поля, где сказано иное.
- **Нельзя отклонять запрос из-за полей, которых нет в DTO**, если клиент их не шлёт. Клиент же шлёт новые поля только тогда, когда сервер показал, что их поддерживает (это отмечено ниже).

## 1. Сверка уже сделанного (пункты 1–3 ТЗ)

### 1.1. Вход через Apple

Клиент отправляет:

```http
POST /auth/apple
{ "identityToken": "<JWT строкой>", "authorizationCode": "<строка>",
  "nonce": "<исходная случайная строка, base64>", "fullName": "<«Имя Фамилия» или отсутствует>" }
```

- `nonce` — **исходное значение**, а в запрос к Apple ушёл его SHA-256 в hex (строчные буквы). Сервер сравнивает `sha256(nonce)` (hex) с claim `nonce` в токене.
- `fullName` приходит только при самом первом входе. Это уже отформатированная строка, а не объект.
- Ответ такой же, как у `/auth/google`: `{"status":"authenticated", "user", "tokens"}` или `{"status":"registration_required", "registrationToken", "profile": { "email", "displayName" }}`.

Регистрация (поля те же, что у Google):

```http
POST /auth/apple/register/code  { "registrationToken", "username", "email"? }
POST /auth/apple/register       { "registrationToken", "username", "displayName", "phone", "code", "email"? }
```

`email` клиент шлёт, только если Apple почту не передал (`profile.email == null`).

**Проверить:** имена полей совпадают. Если у вас другие, пришлите — поправлю клиент.

### 1.2. Обработка медиа

- В ответе `POST /attachments` и во вложении внутри сообщения клиент читает `status`. Значение `"PROCESSING"` означает, что файл ещё обрабатывается. Остальные значения он не различает.
- Собеседнику, пока идёт обработка, клиент показывает заглушку «Обрабатывается…» и файл не качает. Отправителю показывает вложение как обычно. Когда придёт `message.updated` с тем же сообщением (уже без `PROCESSING`), пузырь обновится.
- WS `attachment.processed`: клиент ищет id вложения в `attachmentId`, `attachment.id` или `id` — **пришлите хотя бы одно из них**. Если id совпадает с видео или голосовым своей анкеты, клиент перечитывает `GET /dating/profile/me`.
- `mediaStatus` у видео (и у голосового, см. 2.4): клиент понимает `"PROCESSING"` и `"FAILED"`. **Если у вас ошибка обработки называется иначе, скажите.**
- `durationSec` клиент по-прежнему шлёт — игнорировать его правильно.
- `GET /attachments/:id/poster` — обложка «кружка» и видео анкеты: клиент показывает её сразу, а сам ролик качает по нажатию.

### 1.3. WebSocket

- Клиент подключается **только** с `Authorization: Bearer <access>` и без `?token=`. Переключатель «WebSocket: токен в адресе» можно выключить, когда старые версии приложения перестанут встречаться.
- Каждые 20 секунд клиент шлёт WS-**ping** (control frame). Если pong не пришёл до следующего ping, он переподключается. Сервер должен отвечать pong: обычно библиотека `ws` делает это сама, проверьте, что за прокси (Caddy, Cloudflare) это не выключено.
- Переподключение идёт с паузой 1 → 2 → 4 … до 30 секунд со случайным разбросом. По событию `ready` пауза сбрасывается. Код закрытия `4001` → клиент обновляет токен и подключается снова.

## 2. Функции знакомств (пункты 11–16 ТЗ) — точные контракты

### 2.1. Отмена последнего свайпа

```http
POST /dating/swipes/undo            (без тела)
200 → { "limits": DailyLimits }     // limits можно не присылать — клиент просто не обновит счётчик
```

- В `DailyLimits` (в ответах `GET /dating/feed`, `POST /dating/swipes`, `undo`) добавить **`undoLeft: number`** — сколько отмен осталось сегодня. Кнопка показывается только при `undoLeft > 0`; без поля её нет.
- Отменяется последний свайп пользователя (лайк или пропуск), если из него **не получилась пара**. Рекомендация: не позже чем через 5 минут, не больше 3 раз в сутки (значение по вашему усмотрению).
- После отмены анкета снова должна попадать в ленту: удалить запись свайпа и вернуть потраченный лайк в `likesLeft`.
- Отказ — 4xx с `message` (например, «Время на отмену вышло»). Клиент покажет текст и уберёт кнопку.

### 2.2. Инкогнито и показ активности

```http
GET   /dating/search-settings → { "lookingFor": "FEMALE", "incognito": false, "showActivity": true }
PATCH /dating/search-settings   { "lookingFor": "FEMALE", "incognito": true }       // приходит одно из полей
PATCH /dating/search-settings   { "lookingFor": "FEMALE", "showActivity": false }
→ ответ такой же, как у GET
```

- Переключатели в приложении появляются, только если поля есть в `GET`. `lookingFor` клиент шлёт всегда.
- **incognito = true**: анкету в ленте, сетке анкет и поиске по username видят только те, кого этот человек лайкнул. Пары, чаты и уже отправленные сообщения не затрагиваются.
- **showActivity = false**: у этого человека не отдавать `activity` другим (см. 2.5).

### 2.3. Вопросы в анкете (prompts)

Каталог:

```http
GET /dating/catalog → { …, "prompts": [ { "code": "weekend", "text": "Идеальные выходные — это…" }, … ] }
```

- `text` — на языке из `Accept-Language` (см. раздел 5). Раздел в редакторе появляется, только если `prompts` есть в каталоге.

Анкета (публичная и своя):

```json
"prompts": [ { "code": "weekend", "answer": "Горы и плов с друзьями",
               "status": "APPROVED", "rejectReason": null } ]
```

- В публичной анкете — только `APPROVED`; `status` и `rejectReason` можно не присылать.
- В своей (`GET /dating/profile/me`) — все ответы со `status: PENDING | APPROVED | REJECTED` и `rejectReason`.

Сохранение:

```http
PATCH /dating/profile/me   { …, "prompts": [ { "code": "weekend", "answer": "…" } ] }
```

- Клиент шлёт `prompts`, **только если в каталоге есть `prompts`**. Массив — это полный список ответов: заменить им все прежние, пустой массив удаляет все.
- Ограничения: не больше 3 вопросов, `code` из каталога, без повторов, `answer` — от 1 до 200 символов после trim.
- Модерация: новый или изменённый ответ получает `PENDING`, неизменённый сохраняет статус. Те же фильтры, что для `bio` (ссылки, телефоны, мессенджеры).

### 2.4. Голосовое приветствие

```http
PUT    /dating/profile/me/voice   { "attachmentId": "…" }   → MyDatingProfile (как PUT …/video)
DELETE /dating/profile/me/voice                              → MyDatingProfile
```

- Загрузка идёт как обычно, через `POST /attachments`: multipart, `kind=VOICE`, `audio/mp4` (AAC .m4a). Лимит — 30 секунд, длительность меряет сервер, больше — `videoTooLong` или отдельный код.
- **Своя анкета**: добавить ключ **`voice`** всегда — `null`, если голосового нет. Клиент показывает строку «Голосовое приветствие» только когда ключ `voice` присутствует.

  ```json
  "voice": { "attachmentId": "…", "status": "PENDING", "rejectReason": null, "mediaStatus": "PROCESSING" }
  ```

- **Публичная анкета**: `"voiceId": "…"` и `"voiceDurationSec": 12`, только одобренное модератором.
- Модерация — как у видео анкеты. По WS `dating.voiceModerated` (а также `dating.promptModerated` и `dating.profileEdited`) клиент перечитывает анкету.

### 2.5. Активность («в сети / сегодня / на этой неделе»)

В карточках ленты, сетки, «Вас лайкнули» и в `GET /dating/profiles/:id`:

```json
"activity": "online" | "today" | "week"
```

- `online` — есть живое WS-соединение (или активность меньше 5 минут назад), `today` — меньше 24 часов, `week` — меньше 7 дней. Старше — поле не отдавать.
- Не отдавать, если у человека `showActivity = false`. Точное время не раскрывать.
- Желательно при равной совместимости поднимать в ленте более активных.

### 2.6. Ледоколы

```http
GET /dating/icebreakers?userId=<id>
→ ["Вы оба любите горы — где был последний поход?", …]      // или { "icebreakers": [ … ] } — клиент понимает оба
```

- 3–5 коротких фраз (до 120 символов) по общим интересам, кухне, хобби и цели знакомства, на языке из `Accept-Language`. Если общего нет — общие вежливые фразы или пустой массив.
- Доступно тому, кто может написать этому человеку. Иначе — 403, клиент просто не покажет подсказки.

## 3. Push (APNs)

Клиент уже разбирает эти поля при нажатии на уведомление. Расширение уведомлений меняет текст и картинку до показа.

### 3.1. Общее

- `aps.mutable-content: 1` — **во всех обычных push** (иначе расширение не запускается).
- `aps.thread-id: <chatId>` — уведомления одного чата собираются в стопку. Если его нет, расширение подставит `chatId`.
- `live: true` — событие уже ушло по WS. Если сокет подключён, приложение баннер не покажет (так работает уже сейчас).

### 3.2. Поля по видам (на верхнем уровне payload, рядом с `aps`)

| Событие | Поля | Куда ведёт нажатие |
|---|---|---|
| Сообщение | `chatId`, `messageId`, `senderId`, `type: "message"` | чат |
| Сообщение секретного чата | то же + `ciphertext`, `senderKey` | чат; превью расшифровывается на устройстве |
| Фото в сообщении | то же + `imageUrl` | чат, миниатюра в уведомлении |
| Пара (взаимный лайк) | `matchId`, `chatId` (если чат создан), `type: "dating.match"` | чат или знакомства |
| Вас лайкнули | `type: "dating.liked"` | список «Вас лайкнули» |
| Первое сообщение, запрос | `introId`, `type` | знакомства |
| Встреча | `meetingId`, `matchId`, `type` | знакомства |
| Просьба о новом селфи | `moderation: "dating.selfieRequested"` | Мой профиль → проверка |
| SOS доверенного контакта | `sosId` | экран тревоги |

### 3.3. Секретный чат

- В `aps.alert` — только общий текст («Бо Хам · Новое сообщение»), без имени, если так выбрано в настройках уведомлений.
- Добавить `ciphertext` (как в сообщении, base64), `senderKey` (публичный ключ отправителя, base64), `chatId`, `senderId`. Всё вместе должно укладываться в 4 КБ. Длинный шифротекст не присылать — останется общий текст.
- Расшифровка идёт только на устройстве и только если `senderKey` совпадает с ключом, который приложение уже запомнило для `senderId`. Серверу ничего проверять не нужно.

### 3.4. Картинки

- `imageUrl` — подписанная ссылка на **миниатюру** (JPEG или PNG, до ~300 КБ, сторона до 1024) со сроком жизни около 10 минут. Либо полный `https://…`, либо путь от сервера `/attachments/…?sig=…`. Без заголовка авторизации.
- Для фото с таймером и фото в секретном чате `imageUrl` **не присылать**.

### 3.5. VoIP (звонки) — без изменений

Поле `call` с `callId`, `chatId`, `fromName`, `video`, `isGroup`, `title`, как сейчас.

## 4. Universal Links и веб-страницы

### 4.1. apple-app-site-association

`https://adm.orzu.pro/.well-known/apple-app-site-association`: **без редиректов**, `Content-Type: application/json`, доступен без авторизации, в том числе для CDN Apple (Cloudflare не должен показывать ему проверку «вы человек?»).

```json
{
  "applinks": {
    "details": [
      {
        "appIDs": ["<TEAM_ID>.com.orzuapp.messenger"],
        "components": [
          { "/": "/u/*", "comment": "профиль человека" },
          { "/": "/c/*", "comment": "канал" }
        ]
      }
    ]
  }
}
```

`<TEAM_ID>` — Team ID из Apple Developer (тот же, что для ключа Sign in with Apple).

### 4.2. Страницы для тех, у кого нет приложения

- `GET /u/<username>` — HTML: имя, аватар, кнопка «Открыть в приложении» (`boham://u/<username>`) и «Скачать в App Store». **Никаких** возраста, города, фото анкеты и прочих данных. Если человек запретил поиск по username (`messengerSearchByUsername = false`) или аккаунт удалён или заблокирован — нейтральная страница «Профиль недоступен».
- `GET /c/<username>` — название канала, число подписчиков и те же кнопки.
- Желательно добавить `<meta name="apple-itunes-app" content="app-id=…">` (после публикации в App Store) и Open Graph-теги для превью ссылки в мессенджерах.

### 4.3. Что приложение делает со ссылкой

`/u/<username>` → `GET /users/search?q=<username>` и точное совпадение → карточка человека. `/c/<username>` → `GET /chats/channels/search?q=<username>` и точное совпадение → «Подписаться» → `POST /chats/:id/subscribe`. **Нужно, чтобы поиск находил по точному username**, даже если выдача по подстроке ограничена.

## 5. Язык (пункт 20 ТЗ)

Клиент в **каждом** HTTP-запросе шлёт `Accept-Language: ru | tg | en` — язык интерфейса, который человек выбрал в приложении.

- На этом языке отдавать: `message` ошибок, каталог (`/dating/catalog`: города, интересы, кухни, `prompts`, ступени и вопросы «Пути к браку»), правила сообщества и документы, причины совместимости (`compatibility.reasons`), ледоколы, `AppStatus`/обслуживание.
- Сохранять язык у пользователя (например, при регистрации устройства в `POST /devices` или по последнему запросу) и на нём писать **push и письма** с кодами.
- Нет перевода — отдавать русский. Если перевода на таджикский пока нет, клиент сам переводит свой интерфейс, но тексты с сервера останутся русскими.

## 6. SOS (пункт 6 ТЗ) — под текущий клиент

- Пока тревога открыта и экран SOS на виду, клиент **каждые 30 секунд** шлёт `PATCH /safety/sos/:id/location` с `{ latitude, longitude, accuracyM? }`. Такую частоту нельзя резать rate limit'ом.
- Открытую тревогу клиент восстанавливает после перезапуска через `GET /safety/sos/:id`, поэтому **владелец тревоги должен иметь доступ к этому эндпоинту**. Сейчас он используется для доверенных контактов.
- Доверенный контакт видит путь на карте: `GET /safety/sos/:id/track` → `{ alertId, points: [{ latitude, longitude, accuracyM, recordedAt }] }`, перечитывается с каждым `safety.sos.location`.

## 7. Пункты ТЗ, которые клиент уже использует

- **Докачка событий** (п. 4): клиент помнит последний `seq` и после `ready` запрашивает `GET /sync?since=` до `seq` из `ready`. При `resetRequired` экраны перечитываются целиком.
- **429 + `Retry-After`** (п. 5): срок берётся из заголовка, иначе из `retryAfterSec`. Очередь отправки ждёт этот срок. Подробность `reason` (например, `CODE_ALREADY_SENT`) клиент читает как код ошибки.
- **Загрузка по ссылке** (п. 7): видео анкеты, «кружки», голосовые, файлы и очередь отправки идут через `POST /attachments/uploads` → `PUT` по `uploadUrl` без токена → `POST …/complete`. Фото остаются на `POST /attachments`. `PUT` идёт в фоновой `URLSession`: очередь хранит `uploadId` и после перезапуска дожидается загрузки. Поэтому сервер должен отвечать `409` на повторный `PUT` уже завершённой загрузки, а повторный `complete` должен возвращать то же вложение. Пока первый `complete` ещё обрабатывает файл, повтор получает `409` с `code: "uploadInProgress"` — очередь повторяет его через несколько секунд.
- **Пересылка** (`POST /chats/:id/messages/forward`): приложение передаёт `forwardId` (UUID на один экран выбора чата). Повтор с тем же `forwardId` не создаёт дублей, а досылает недосланное.
- **429 в очереди отправки**: ждёт только сообщение, упёршееся в лимит, и его чат; остальные чаты отправляются.
- **`POST /chats/:id/screenshot`** (п. 9): клиент отправляет его при снимке экрана в секретном чате (без `messageId`) и при открытом фото с таймером (с `messageId`). Служебное сообщение `systemEvent: "screenshot"` показывается строкой по центру.
- **Ротация E2E-ключей** (п. 10): `recipientKeyId` уходит при отправке и **правке**. Свои старые сообщения клиент расшифровывает ключом из `GET /users/:id/e2e-keys/:keyId`, чужие — ключом из `senderKey`, если этот ключ был подтверждён раньше. По `e2e.keyChanged` клиент сразу показывает предупреждение. У цитаты (`replyTo`) сервер отдаёт `recipientKeyId`: так цитата своего старого сообщения тоже расшифровывается.

Ещё не подключены: **подписка через StoreKit 2** (п. 18) и **ссылка «показать анкету семье»** (п. 19).

- Team ID подставить в apple-app-site-association (раздел 4.1).
